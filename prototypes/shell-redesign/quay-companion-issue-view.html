        Your runs of the job

        Counted live in the mock: every press inside the window is a click, and pointer travel is the straight-line distance between presses. Typing is not counted. The table keeps your best run per layout and resets when the page reloads. Today this job leaves Quay for the browser.

        My recommendation

        B · Status card first, pull request shown first when both are linked

        • It is the same shape as the pull request view you chose (readiness card on top, cells open detail), so a ticket and a pull request read alike in the companion.
        • It arrives on what needs you: an open blocker, or a new comment from the agent.
        • The card's one button changes with the ticket's state (Implement, Open blocker, Open pull request, Reopen), which is the next step of the loop.
        • Close keeps GitHub's reasons (completed, not planned, duplicate) and becomes Close with comment once you type, so recording a resolution is one press.
        • Edits that are rare in the loop (description, milestone, project fields, relationships) stay on GitHub behind an Open on GitHub link.

        The cost: in my own run of the job, following the outline, B took 9 clicks where A took 7 and C took 8, because assignees and labels sit one cell away. I judge that worth it, since assigning and labelling are rarer in the loop than reading what the agent said.
